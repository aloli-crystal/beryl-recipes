Official Aloli recipes for
https://github.com/aloli-crystal/beryl[beryl] —
the Crystal provisioner for bare-metal FreeBSD servers.

NOTE: This repository complements beryl. It holds the *YAML recipes*
that declare the desired state of a FreeBSD server: packages, services,
users, sshd configuration, firewall, etc. The execution logic (the
*primitives*) lives in the beryl binary. The recipes live here,
versioned and forkable.

== Overview

beryl orchestrates recipes through the `beryl apply <host>` command.
Recipes are read from:

. *The host orchestration folder* : `~/.config/beryl/<company>/<domain>/<host>/`
. *Additional taps* : `~/.config/beryl/recipes-taps/<name>/recipes/`
. *The main repository* (this one) : `~/.config/beryl/recipes/recipes/`

beryl resolves `requires:` recursively and applies a topological sort.
Every applied recipe is *idempotent* : re-running `beryl apply` only does
what is not already in the desired state.

== Recipe format

[source,yaml]
----
# recipes/<name>.recipe.yml
recipe: <name>                    # optional (derived from the filename)
description: A short sentence stating what the recipe does

requires:                         # other recipes to run first (optional)
  - freebsd-updates
  - other-recipe

parameters:                       # typed parameters, optional
  users:
    type: array
    required: true
    items: string
    description: List of affected users
  notify_email:
    type: string
    default: admin@example.com

steps:                            # primitives or other recipes invoked
  - pkg-install:
      packages: [zsh, git, curl]
  - file-template:
      path: /etc/example.conf
      content: |
        # Template with simple interpolation
        notify={{ notify_email }}
  - service-enable:
      name: example
----

=== Atomic recipe vs aggregate recipe

* *Atomic* : few `requires:`, many `steps:`. Achieves one precise
  concern (e.g. `ohmyzsh`, `ssh-hardening`).
* *Aggregate* (« meta-recipe ») : many `requires:`, few or no `steps:`.
  Composes a typical path (e.g. `post-install`, `web-server`).

beryl treats both the same way — no type distinction, no special
keyword. A recipe is a recipe.

=== Aggregate example

[source,yaml]
----
# recipes/post-install.recipe.yml
recipe: post-install
description: Standard Aloli post-install for FreeBSD
requires:
  - freebsd-updates
  - firewall-pf
  - ssh-hardening
  - ohmyzsh
  - ruby
  - nginx-passenger
  - nginx-hardening
# no steps: everything is in the requires
----

== Conventions

[cols="2,3", options="header"]
|===
| Aspect | Convention

| File naming
| `<name>.recipe.yml` in lowercase kebab-case (e.g. `nginx-passenger.recipe.yml`,
  not `NginxPassenger.recipe.yml` nor `nginx_passenger.recipe.yml`).

| Recipe naming
| Optional: the name is derived from the file (without `.recipe.yml`) ; if present, it must match.
  beryl checks it at load time.

| Field order
| `recipe`, `description`, `requires`, `parameters`, `steps`. Not
  mandatory but readable.

| Description
| A short single-line sentence that fits in the output of a future
  `beryl recipes list`.

| Indentation
| 2 spaces, never tabs (consistent with the host-side beryl YAML).

| Characters
| UTF-8, no BOM.
|===

== How to fork for your own recipes

Three possible approaches, by increasing complexity:

=== 1. Per-host folder override (simplest case)

To adapt an official recipe for *one particular host*, create a local
copy in the host folder:

[source,sh]
----
cd ~/.config/beryl/<company>/<domain>/<host>
cp ../../../recipes/recipes/ohmyzsh.recipe.yml ./ohmyzsh.recipe.yml
vim ohmyzsh.recipe.yml                  # adapt freely
----

beryl takes the local copy in priority. No fork needed.

=== 2. Additional tap (multi-host, multi-client case)

For a *set of in-house recipes reused across several hosts*, create a
separate git repository and declare it as a tap:

[source,sh]
----
beryl recipes-tap add https://github.com/<you>/private-recipes.git
----

beryl clones into `~/.config/beryl/recipes-taps/private-recipes/` and
resolves it with a higher priority than the main repository.

NOTE: The `recipes-tap` mechanism is still being designed. See beryl
`apply-recipes-architecture.adoc`, section « Open questions ».

=== 3. Forking the main repository (extreme case)

To fully rewrite the common core (rare), fork this repository and point
beryl at your fork:

[source,yaml]
----
# ~/.config/beryl/_default.yml
recipes:
  repo_url: https://github.com/<you>/beryl-recipes.git
  branch: production
----

== How to contribute

. Fork this repository
. Create a `feat/<recipe-name>` branch from `production`
. Add your recipe under `recipes/<name>.recipe.yml`
. If the recipe deserves a test, add it under `tests/`
. Open a *Pull Request* against `production` with:
+
* The business need: what the recipe is for
* The test (if any)
* A field check (which FreeBSD version(s) you validated it on)

Recipes accepted into this main repository must be:

* *FreeBSD-native* (no Linuxisms — `pw`, not `useradd` ; `service`, not
  `systemctl` ; `pkg`, not `apt`).
* *Generic* (usable by any beryl user, not Aloli-specific).
* *Idempotent* (re-running `beryl apply` several times must be a no-op).
* *Documented* (clear description, typed parameters, a usage example in
  a comment if non-trivial).

For recipes specific to a client, to a particular infrastructure, or
experimental, use a *tap* (option 2 above) rather than submitting a PR
to the main repository.

== Repository layout

[source,text]
----
beryl-recipes/
├── README.adoc                  # this file (English, canonical)
├── README.fr.adoc               # French version
├── LICENSE                      # MIT
├── CHANGELOG.adoc               # one entry per recipe added/changed
├── recipes/                     # all recipes (empty in phase 0)
│   ├── .gitkeep
│   └── <name>.recipe.yml        # one recipe
└── tests/                       # integration tests (empty in phase 0)
    └── .gitkeep
----

No `meta-recipes/` vs `recipes/` split — every recipe lives in
`recipes/`, with a uniform format.
