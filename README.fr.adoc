Recettes officielles Aloli pour
https://github.com/aloli-crystal/beryl[beryl] —
le provisionneur Crystal pour serveurs FreeBSD bare-metal.

NOTE: Ce dépôt est complémentaire à beryl. Il contient les
*recettes YAML* qui déclarent l'état désiré d'un serveur FreeBSD :
packages, services, users, configuration sshd, firewall, etc.
La logique d'exécution (les *primitives*) vit dans le binaire
beryl. Les recettes vivent ici, versionnées, forkables.

== Vue d'ensemble

beryl orchestre les recettes via la commande `beryl apply <host>`.
Les recettes sont lues depuis :

. *Le dossier d'orchestration du host* : `~/.config/beryl/<société>/<domaine>/<host>/`
. *Les taps additionnels* : `~/.config/beryl/recipes-taps/<nom>/recipes/`
. *Le dépôt principal* (ce dépôt-ci) : `~/.config/beryl/recipes/recipes/`

Beryl résout les `requires:` récursivement et applique le tri
topologique. Chaque recette appliquée est *idempotente* : relancer
`beryl apply` ne fait que ce qui n'est pas déjà à l'état désiré.

== Format d'une recette

[source,yaml]
----
# recipes/<nom>.recipe.yml
recipe: <nom>                     # facultatif (dérivé du nom de fichier)
description: Une phrase courte qui dit ce que fait la recette

requires:                         # autres recettes à exécuter avant (facultatif)
  - freebsd-updates
  - autre-recette

parameters:                       # paramètres typés, facultatif
  users:
    type: array
    required: true
    items: string
    description: Liste des users concernés
  notify_email:
    type: string
    default: admin@example.com

steps:                            # primitives ou autres recettes appelées
  - pkg-install:
      packages: [zsh, git, curl]
  - file-template:
      path: /etc/example.conf
      content: |
        # Template avec interpolation simple
        notify={{ notify_email }}
  - service-enable:
      name: example
----

=== Recette atomique vs recette agrégat

* *Atomique* : peu de `requires:`, beaucoup de `steps:`. Réalise
  un domaine précis (ex: `ohmyzsh`, `ssh-hardening`).
* *Agrégat* (« méta-recette ») : beaucoup de `requires:`, peu ou
  pas de `steps:`. Sert à composer un parcours type (ex:
  `post-install`, `web-server`).

beryl traite les deux pareillement — pas de distinction de type,
pas de mot-clé spécial. Une recette est une recette.

=== Exemple agrégat

[source,yaml]
----
# recipes/post-install.recipe.yml
recipe: post-install
description: Post-install Aloli standard pour FreeBSD
requires:
  - freebsd-updates
  - firewall-pf
  - ssh-hardening
  - ohmyzsh
  - ruby
  - nginx-passenger
  - nginx-hardening
# pas de steps : tout est dans les requires
----

== Conventions

[cols="2,3", options="header"]
|===
| Aspect | Convention

| Nommage de fichier
| `<nom>.recipe.yml` en kebab-case minuscule (ex: `nginx-passenger.recipe.yml`,
  pas `NginxPassenger.recipe.yml` ni `nginx_passenger.recipe.yml`).

| Nommage du recipe
| Facultatif : le nom est dérivé du fichier (sans `.recipe.yml`) ; si présent, doit correspondre.
  beryl le vérifie au chargement.

| Ordre des champs
| `recipe`, `description`, `requires`, `parameters`, `steps`. Pas
  obligatoire mais lisible.

| Description
| Une phrase courte qui tient sur une ligne dans la sortie d'un
  futur `beryl recipes list`.

| Tabulation
| 2 espaces, jamais de tabs (cohérent avec les YAML beryl côté
  host).

| Caractères
| UTF-8, pas de BOM.
|===

== Comment forker pour ses propres recettes

Trois approches possibles, par ordre de complexité :

=== 1. Override par dossier host (cas le plus simple)

Pour adapter une recette officielle à *un host particulier*,
créez une copie locale dans le dossier du host :

[source,sh]
----
cd ~/.config/beryl/<société>/<domaine>/<host>
cp ../../../recipes/recipes/ohmyzsh.recipe.yml ./ohmyzsh.recipe.yml
vim ohmyzsh.recipe.yml                  # adaptez librement
----

beryl prend la copie locale en priorité. Pas besoin de fork.

=== 2. Tap additionnel (cas multi-hosts, multi-clients)

Pour un *jeu de recettes maison réutilisé sur plusieurs hosts*,
créez un dépôt git séparé et déclarez-le comme tap :

[source,sh]
----
beryl recipes-tap add https://github.com/<vous>/private-recipes.git
----

beryl clone dans `~/.config/beryl/recipes-taps/private-recipes/` et le
résout avec priorité plus haute que le dépôt principal.

NOTE: Le mécanisme `recipes-tap` est en cours de design. Voir
beryl `apply-recipes-architecture.adoc` section
« Questions ouvertes ».

=== 3. Fork du dépôt principal (cas extrême)

Pour réécrire intégralement le tronc commun (rare), forkez ce
dépôt et pointez beryl vers votre fork :

[source,yaml]
----
# ~/.config/beryl/_default.yml
recipes:
  repo_url: https://github.com/<vous>/beryl-recipes.git
  branch: production
----

== Comment contribuer

. Forkez ce dépôt
. Créez une branche `feat/<nom-recette>` depuis `production`
. Ajoutez votre recette dans `recipes/<nom>.recipe.yml`
. Si la recette mérite un test, ajoutez-le dans `tests/`
. Ouvrez une *Pull Request* vers `production` avec :
+
* Le besoin métier : à quoi sert la recette
* Le test (si présent)
* Une vérification terrain (sur quel(s) FreeBSD vous l'avez
  validée)

Les recettes acceptées dans ce dépôt principal doivent être :

* *FreeBSD-natives* (pas de Linuxismes — `pw`, pas `useradd` ;
  `service`, pas `systemctl` ; `pkg`, pas `apt`).
* *Génériques* (utilisables par n'importe quel utilisateur de
  beryl, pas spécifiques à Aloli).
* *Idempotentes* (relancer `beryl apply` plusieurs fois doit
  être un no-op).
* *Documentées* (description claire, paramètres typés, exemple
  d'usage en commentaire si non trivial).

Pour les recettes spécifiques à un client, à une infra
particulière, ou expérimentales, utilisez un *tap* (option 2
ci-dessus) plutôt que de soumettre une PR au dépôt principal.

== Layout du dépôt

[source,text]
----
beryl-recipes/
├── README.adoc                  # ce fichier
├── LICENSE                      # MIT
├── CHANGELOG.adoc               # une entrée par recette ajoutée/modifiée
├── recipes/                     # toutes les recettes (vide en phase 0)
│   ├── .gitkeep
│   └── <nom>.recipe.yml         # une recette
└── tests/                       # tests d'intégration (vide en phase 0)
    └── .gitkeep
----

Pas de séparation `meta-recipes/` vs `recipes/` — toutes les
recettes vivent dans `recipes/`, format uniforme.
